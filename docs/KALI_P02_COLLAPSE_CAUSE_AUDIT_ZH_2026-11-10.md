# KaliBench P02 输出退化排查（2026-11-10）

## 已确认的故障

P02 在 128 道内部开发题中有 **126 道仅生成一个换行 token，下一步就生成 EOS**。这 126 道均未达到 1024-token 上限，也没有被截断；模型确实提前结束，而非评分器丢失命令。原模型在相同开发题上没有出现仅换行的回答。P02 的严格正确数为 **47/128 → 2/128**，格式错误为 **5 → 126**；此前 `1e-5` 的 638 条 SFT 在共同的 64 题上为 **28/64 → 30/64**。因此维持 E0，不采用 P02。这些题来自官方 TRAIN 的内部开发划分，不是 KaliBench 官方 TEST 结果。

训练编码核查表明，638 条监督目标都以“换行、`</think>`”开头，并以 EOS 结束。P02 能生成第一个换行，却在本应继续生成 `</think>` 的位置提前选择 EOS。这说明当前故障发生在模型的续写选择；仅凭输出还不能判断是哪个训练差异使 EOS 成为首选。

## 对照核查

- 已找回并核对两次运行各自真正执行的 Worker 哈希。P02 与此前表现较稳定的 638 条 SFT 使用**逐条相同的 638 条训练记录及顺序**，共同的 64 道开发题和四道基线锚点也相同；模型检查点、运行依赖、LoRA 配置及随机种子一致。共同 64 题的原模型严格正确数均为 **28/64**，原生平均分均为 **0.756287**。
- 此前 SFT 的学习率为 `1e-5`，P02 为 `5e-6`。P02 还在训练前额外运行了 128 道基线推理，且两次运行分别落在 A100 PCIe 与 A100 SXM4 上。首步训练损失均为 **2.41219**；之后抽样记录的损失均值分别约为 **0.617** 与 **0.909**。抽样日志不能代替完整训练曲线。
- 两份保存的 LoRA adapter 各有 **144 个 FP32 张量**，哈希均与训练回执匹配，重载探针的最大 logit 差为零。P02 的 LoRA B 张量总范数约为旧模型的 **75%**。这与更新较弱相符，但范数不能单独证明性能退化的原因。
- P01 的 `1e-5` 冒烟实验只有 **505 条训练记录、274 个工具**；638 条全集有 **359 个工具**。因此 P01 退化不能被当作“`1e-5` 学习率过高”的单变量证据。

## 仍需验证

现有证据把故障定位到**模型生成阶段过早输出 EOS**，并使较低学习率下的格式学习不足成为主要假设；还不能把学习率单独确定为根因。已冻结 P04 对照：沿用 P02 的 Worker、数据、训练前基线推理、两块开发集及 A100 SXM4 型号，只把训练学习率恢复到 `1e-5`。P04 是操作员固定的因果诊断，**不是 ABA 代理选择的新候选**。P04 因目标 A100 SXM4 无空位，排队约 **70 分钟**后在预设最晚安全启动点取消；取消前 Pod 未分配节点，**没有训练步数或评分结果**，个人 Job、Pod、ConfigMap 和 Secret 均已清理。若将来运行 P04 后恢复正常，学习率差异将获得强支持；若仍提前 EOS，就需继续分离训练前推理与设备数值路径。

原生 ABA 训练运行中的 Broker 回执字段错误是另一项编排问题，已通过单独恢复运行完成原生评分与 E0 选择；它不能解释 P02 已保存在 GPU Job 中的提前 EOS。官方 TEST 与封存最终 64 题均未使用，E0 仍是默认模型。
