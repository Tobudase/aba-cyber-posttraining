# KaliBench 原生 ABA P05：训练完成，开发集门槛未通过（2026-11-11）

## 研究问题和数据边界

目标是让 ABA 在冻结协议下选择并训练一个公开权重的网络安全模型候选，再比较原底座 E0 与候选 P05。底座是 RedSage-K 8B。训练使用经过发布方筛选的 KaliBench 官方 TRAIN 中 638 行；评分使用同样来自官方 TRAIN、与训练行分开的两组内部开发题，共 128 题。这些标签属于发布方 silver，不是独立专家 gold。**官方 TEST 使用 0 行；封存 final64 使用 0 行。** 因此以下分数不是官方 KaliBench 排名，也不证明独立泛化。

## 执行和计分

ABA 的 Setup 及独立 reviewer 通过后，Designer 选择 P05（学习率 `1e-5`、seed 42）。Worker 提交了一个真实的 A100-SXM4-80GB 训练任务，完成 638/638 个具有非零梯度的优化步骤；144 个 LoRA 张量发生变化，适配器重载核查的 logit 差为 0。任务结束后，其自有计算资源已清理。最初的原生运行在训练完成后因为 Broker 回执遗漏 `nonzero_gradient_steps` 字段而中断；修正字段后，独立的 CPU 恢复运行复用了**已有** P05 回执、适配器和冻结评分，未再提交 GPU 任务。这不是一条从头到尾不中断的原生运行。

冻结准入门槛要求原生平均分提高、严格正确不降、未见工具严格正确不降、格式错误不增、零截断。P05 只在第一项失败，因此所有门槛未通过；保护评分给 P05 `−1`，E0 为 `0`。**正式选择保留 E0，不推广 P05。**

## 对照与错误核查

同批数据上的 P04 是由操作员执行的匹配学习率对照：严格正确 54/128、原生平均分 0.77569、格式错误 0。但 P04 并非 ABA 选择的候选；P04 与 P05 各只有一次训练。两者不同的原因尚未被隔离，不应将 P04 的开发集增益移植为 P05 或 ABA 的结论。

一次 CPU 恢复运行的冻结评分成功，但 finalizer 的沙箱无法读取指令指定的私有 E0 目录，错误地从 P05 候选目录复制了四个文件。原生 finalizer 的格式 verifier 仍报告通过；宿主的选择门槛检查将这份 P05 交付判为无效。这说明“工作流 completed”和“模型选择正确”需要分别核验。另由操作员只读收集的 E0 四文件与 Setup 来源哈希逐字节一致；该核查包不冒充原生 finalizer 交付。

第二次 CPU 恢复把 E0 改为 finalizer 可读取的只读输入，finalizer 确实交付了哈希正确的 E0。然而 Worker 提前将 E0 文件复制进候选目录，导致保护评分程序评的是 E0（0 分）而非 P05（应为 −1 分）；宿主当时的 `COMPLETE` 状态没有检查候选身份，因此这次运行也不能算完整的 P05 候选评分闭环。后续收集门槛已增加“候选评分必须恰好为 P05 的 −1 分”，并禁止 E0 在 Setup 之后再次作为候选评分。

第一次针对该错误的门槛修订过于严格：原生 Setup verifier 会自动复核 E0，因此简单限制 E0 只评分一次使 Setup verifier 失败。该轮在候选执行前被停止，VM 与自有资源均已清理。最终规则允许 Setup 及其 verifier 复核 E0，但禁止 P05 提交后、候选保护评分前再次把 E0 当作候选。规则的本机边界测试已通过，仍需以原生运行结果为准。

**最终恢复核查：通过。** 在新的独立 CPU 原生恢复运行中，Setup verifier、Setup reviewer、Worker attempt verifier 和 finalizer verifier 均通过；保护评分节点对 **P05 给出 −1.0**，finalizer 选择 **E0**。宿主再独立核对交付的四份文件均与冻结 E0 基线逐字节相同，运行终态为 `completed`。该恢复新增 GPU Job 为 0，官方 TEST 使用 0 行；运行后 VM 已停止，个人标签下无残留 Job、Pod、ConfigMap 或 Secret。它补全了原有真实 GPU 训练结果的评分与交付流程，但仍是**分开的恢复运行**，不是一条从训练到交付都不中断的单次运行。

结论仅限上述 TRAIN 来源的内部开发集。要做模型推广，还需要独立来源的可信标签、与目标评测对齐的验证，以及预先固定的决策规则。当前没有正式测试提升或已推广的新模型。
