# KaliBench P02：Agent 提交的后训练候选及失败门控

原生 ABA 的设计代理选择预注册配方 P02，Worker 在 Setup 验证和审查通过后提交了唯一的 A100 Job。RedSage-K 8B 在 638 条出版方标记的官方 TRAIN 样本上进行 BF16 LoRA SFT，学习率 `5e-6`。Job 完成了 **638/638 次非零梯度优化步**；保存的 adapter 重载前后最大 logit 差为 0。128 题开发集的基线和候选预测均已收集，个人 Job、Pod 与输入资源残留为 0。

| 128 题内部开发指标 | 原模型 E0 | P02 |
| --- | ---: | ---: |
| 严格正确 | 47 | 2 |
| 原生总分均值 | 0.7550 | 0.2292 |
| 格式错误 | 5 | 126 |

P02 的 126 个回答仅输出换行后结束，未通过总分、严格正确、未见工具和格式保护门槛。**不采用 P02；E0 仍是默认模型。**这些开发题来自官方 TRAIN，和训练题按 ID 隔离；官方 TEST 与封存的 64 题最终确认集均未使用。这不是 KaliBench 官方榜单结果，也不是独立专家标注的结论。

本次原生 ABA 编排**没有完成**：GPU 收集器验证完训练后，Broker 要求读取 `changed_tensors`，但导出的回执没有这个字段，导致 Worker 错误地收到 `FAILED`，未完成原生评分与最终选择。上表由预先冻结的同一内部评分器在本机对真实 GPU 预测离线计算，不能写成原生 ABA 已完成。失败后虚拟机停止，个人 GPU Job 与输入对象均已清理。

首次尝试用已有 P02 回执执行不新增 GPU Job 的原生评分恢复时，Setup 代理修改了受哈希保护的 README，审查又因时间预算耗尽而失败。之后的独立 CPU 恢复运行通过原生 Setup 验证与审查、Designer、Worker、评分和最终器验证；它核对既有的真实 P02 训练回执，原生评分给 P02 **−1**，最终选择 **E0**。最终交付的 `run.py`、`README.md`、`train_metrics.json`、`final_model/model.json` 与受保护的 E0 零步基线逐字节相同。本次恢复没有新建 GPU Job，虚拟机已停止，个人 Job、Pod、ConfigMap、Secret 残留为零。这是一条**单独完成的恢复运行**，不能把原先在 Broker 处失败的训练运行改写成一次无故障端到端运行；也不能把它解释为 P02 带来收益。确定性离线审计与原生恢复运行的最终选择一致，均为保留 E0。

与此前较稳定的 638 条 SFT 相比，P02 的训练样本、模型权重、LoRA 配置和随机种子相同；学习率不同，且 P02 在训练前额外运行了 128 题基线推理。现有比较不能单独确认哪一项导致输出塌缩。下一步先修复回执契约，再用受控实验隔离训练前推理和学习率的影响，避免重复运行已知退化的配方。
